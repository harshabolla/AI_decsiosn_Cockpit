OPella AI DECISION COCKPIT
Complete Project Context & Architecture Specification

You are working on an enterprise-grade AI + Data Engineering platform called:

Opella AI Decision Cockpit

The goal is to build a production-oriented conversational analytics platform where business users can ask natural-language questions about Commercial, Finance and Supply Chain data and receive:

trusted answers
governed SQL
interactive charts
KPI explanations
supporting evidence
relevant business guidelines
RAG-based knowledge
explainable execution traces
optional operational actions through ServiceNow
secure enterprise-grade AI behavior

This is NOT intended to be a simple chatbot.

It is an:

Agentic AI + Data Engineering + Semantic Layer + RAG + MCP + Snowflake + dbt + Enterprise Governance platform.

The system should demonstrate the architecture and engineering practices expected from a Senior AI/Data Engineer.

1. BUSINESS PROBLEM

Opella has business data across areas such as:

Commercial / Sales
Finance
Supply Chain
Inventory
Products
Geographies

The system converts these natural-language requests into governed analytical workflows.

4. WHY LANGGRAPH

LangGraph is used because this is not a single LLM call.

The workflow requires:

security
→ intent
→ semantic understanding
→ analytics
→ SQL generation
→ SQL validation
→ data retrieval
→ knowledge retrieval
→ review
→ visualization
→ response

Some paths may branch.

For example:

Normal analytics question
        ↓
Analytics workflow

while:

ServiceNow request
        ↓
OperationsAgent
        ↓
Approval
        ↓
ServiceNow

The agents communicate through shared typed state.

Agents should NOT directly call each other.

Correct:

Agent A
 ↓
LangGraph State
 ↓
Supervisor
 ↓
Agent B

Incorrect:

Agent A
 ↓
Agent B.execute()
5. BASE AGENT ARCHITECTURE

All agents should follow a common abstraction.

Example:

class BaseAgent(ABC):

    @abstractmethod
    async def execute(self, state):
        ...

    def validate_input(self, state):
        ...

    def metadata(self):
        ...

Agents should follow SOLID principles.

Responsibilities must remain separated.

7. SEMANTIC LAYER

The semantic layer is critical.

It prevents the LLM from inventing business definitions.

Example:

net_sales

has:

definition
source table
source column
aggregation
grain
allowed dimensions
business rules

Example:

{
  "metric": "net_sales",
  "definition": "Sales after applicable deductions",
  "aggregation": "SUM",
  "table": "fact_sales",
  "column": "net_sales"
}

The SQL generator receives this governed context.

9. SQL PLANNER

The SQL planner creates an intermediate representation.

Example:

User:

"Show monthly net sales for Doliprane in India."

Planner:

{
  "metric": "net_sales",
  "dimensions": ["month"],
  "filters": {
    "product": "Doliprane",
    "country": "India"
  },
  "aggregation": "sum",
  "time_range": "required"
}

This makes SQL generation more deterministic.

10. SQL GENERATOR

Architecture:

The SQL generator receives:

question

It generates structured output:

{
  "sql": "...",
  "tables": [],
  "columns": [],
  "filters": [],
  "assumptions": []
}
11. SQL VALIDATOR

Never directly execute LLM-generated SQL.

Pipeline:

Generated SQL
      ↓
Parser
      ↓
Syntax validation
      ↓
Read-only validation
      ↓
Table authorization
      ↓
Column authorization
      ↓
Join validation
      ↓
Policy validation
      ↓
Limit/cost controls
      ↓
Execution

Reject destructive operations such as:

DROP
DELETE
UPDATE
INSERT
MERGE
TRUNCATE
ALTER
GRANT
REVOKE

unless an explicitly authorized workflow exists.

42. FINAL OBJECTIVE

The final system should be capable of demonstrating this story:

"We built an enterprise AI decision cockpit where business users can ask natural-language questions against governed enterprise data. LangGraph orchestrates specialized agents through typed state. The semantic layer translates business terminology into governed metrics and dimensions. The Analytics Agent creates an analytical plan, a dedicated SQL generator produces structured SQL, deterministic validators enforce security and schema rules, and the approved query is executed through Snowflake/MCP. RAG provides contextual knowledge and policies from unstructured documents. A reviewer validates the result before a visualization agent creates the appropriate chart. ServiceNow is exposed through controlled tools with human approval for write operations. A provider abstraction allows OpenAI, Anthropic, Bedrock, Gemini and Grok to be used without changing agent code. The complete workflow is observable, auditable, evaluated and protected against prompt injection and PII leakage."

That is the system we are building.

Do not reduce it to a chatbot.

Do not reduce it to text-to-SQL.

Do not reduce it to RAG.

It is an:

Enterprise Agentic AI Decision Platform
combining Data Engineering + Semantic Analytics + LLMs + RAG + MCP + Governance.
